# 협업 규칙 합의문 (3팀)

11월 18일 제안발표 항목 3(협업 규칙 합의문)을 위해 팀이 합의한 내용을 적는다. 근거: 텀프로젝트 공고문(개발 규칙, 공통 모듈 규칙), 스켈레톤 코드 구조와 구현 순서(5. 충돌이 잦은 곳, 7. 자동 검사), 제안발표 안내(발표 항목 3).

## 1. 브랜치 이름 규칙

### 기본 원칙

- main 브랜치에는 직접 올리지 않는다. 모든 작업은 main에서 새 브랜치를 만들어 시작하고, 병합 요청(PR)으로 올린다.
- 한 브랜치에는 한 가지 변경만 담는다. PR 하나에 브랜치 하나를 쓴다.
- 브랜치 이름은 영어 소문자와 하이픈(`-`)만 쓴다.
- **main 브랜치 보호 규칙**: 승인 1명 이상, 자동 검사 3종 통과, force push 금지, 브랜치 삭제 금지, 규칙 우회 목록 비움. 병합 방식은 **병합 커밋(merge commit)만** 쓴다 — 스쿼시·리베이스 병합은 쓰지 않는다.
- **force push / 커밋 이력 재작성(amend, rebase) 금지.** 이미 병합된 커밋을 잘못 올렸으면 `git revert`로 되돌리는 새 커밋을 만든다.

### 형식

```
종류/범위-내용
```

- **종류**: 아래 표의 6가지 중 하나
- **범위**: 기능 번호 `f1` ~ `f6` (공통 모듈은 고치는 기능 번호나 파일 이름, 팀 공동 작업은 작업 이름)
- **내용**: 무엇을 하는지 짧은 영어

| 종류 | 쓰는 경우 | 예시 |
| --- | --- | --- |
| `feat` | 기능 파일·명령 구현 (테스트 포함) | `feat/f1-add-expense` |
| `common` | 공통 모듈(`moim/common/`) 변경 | `common/f1-ledger-insert` |
| `team` | 팀 공동 작업 | `team/integration-test` |
| `fix` | 이미 병합된 코드의 버그 수정 | `fix/f3-period-total` |
| `docs` | 문서 | `docs/working-rules` |
| `chore` | 정리·설정 | `chore/remove-desktop-ini` |

### 헷갈릴 때 고르는 순서

1. `moim/common/` 안의 파일을 고치나? → `common`
2. 이미 병합된 코드를 고치나? → `fix`
3. 내 기능을 새로 만드나? → `feat`
4. 팀 공동 작업인가? → `team`
5. 문서인가? → `docs`
6. 그 외 정리·설정인가? → `chore`

팀 공동 작업이라도 공통 모듈을 고치면 `common`을 쓴다. (예: 자료 파일 손상 대응 → `common/store-recover`)

### 상황별 예시

| 상황 | 브랜치 이름 |
| --- | --- |
| 기능 1 담당이 `ledger.insert`를 채움 | `common/f1-ledger-insert` |
| 기능 1 담당이 지출 추가 명령과 테스트를 만듦 | `feat/f1-add-expense` |
| 기능 4 담당이 `store.py`에 `locks` 항목을 추가 | `common/f4-store-locks` |
| 기능 3 담당이 월별 합계 버그를 고침 | `fix/f3-month-total` |
| 자료 파일 손상 대응 담당이 복구 기능을 만듦 | `common/store-recover` |
| 통합 시나리오 테스트 담당이 테스트를 작성 | `team/integration-test` |
| 협업 규칙 합의문을 올림 | `docs/working-rules` |
| `.gitignore`를 정리함 | `chore/update-gitignore` |

### 같은 기능을 여러 번 작업할 때

- 요구사항마다 새 브랜치를 만든다.
  - 예: `feat/f1-add-expense` → `feat/f1-list-expense` → `feat/f1-edit-delete`
- 병합이 끝난 브랜치는 다시 쓰지 않는다.
  - 새로 만드는 작업이면 `feat`, 이미 병합된 것을 고치면 `fix`로 새 브랜치를 만든다.
- PR이 병합되기 전에 검토 의견을 받아 고칠 때는 같은 브랜치에 커밋을 더 올린다.

### 작업 순서

```powershell
# 1. 새 작업 시작할 때: 최신 main에서 브랜치 만들기
git checkout main
git pull origin main
git checkout -b 종류/범위-내용

# 2. 작업 후 커밋 (파일을 지정해서 add)
git add 바꾼파일
git commit -m "종류(범위): 내용"

# 3. PR 올리기 전에: 최신 main 합치고 검사 3종 실행
git pull origin main
python -m compileall .
python tools/check_imports.py
python -m unittest discover -s tests

# 4. 올리기
git push -u origin 종류/범위-내용
```

- `git pull` 하기 전에 하던 작업은 먼저 커밋한다.
- 충돌이 나면 두 사람의 변경을 모두 살리고, 모르면 그 코드를 쓴 사람에게 묻는다.

### 병합 후 정리

- 병합이 끝난 브랜치는 만든 사람이 지운다.
- 열려 있는 PR이 연결된 브랜치는 지우지 않는다.
- 다른 사람이 만든 브랜치는 만든 사람에게 먼저 묻는다.

```powershell
git push origin --delete 브랜치이름
git branch -d 브랜치이름
```

## 2. 커밋 메시지 형식

브랜치 이름과 짝을 맞춰 `종류(범위): 내용` 형식을 쓴다. 종류·범위는 1장의 분류를 그대로 쓴다.

```
종류(범위): 한 일을 한 줄로
```

예시:

- `common(f1): ledger.insert 구현`
- `feat(f1): 지출 추가 명령과 테스트 추가`
- `fix(f3): 월별 합계가 삭제된 지출을 포함하던 문제 수정`
- `team(integration-test): 한 달치 시나리오 테스트 추가`
- `docs(working-rules): 협업 규칙 합의문 추가`

- 한 줄 제목은 50자 안쪽으로 짧게 쓰고, 설명이 더 필요하면 빈 줄을 하나 띄우고 본문에 적는다.
- "수정", "작업", "업데이트"처럼 무엇을 했는지 알 수 없는 메시지는 쓰지 않는다.
- 커밋을 올리기 전 `git config user.email`이 자기 GitHub 계정 이메일과 같은지 확인한다(다르면 기여로 인정되지 않는다).

## 3. 병합 요청(PR)에 적을 내용

PR 설명에는 아래 세 가지를 반드시 적는다. 공통 모듈을 바꾸는 PR은 추가로 "어느 기능이 이 함수를 쓰는지"도 적는다.

```markdown
## 변경 내용
(무엇을 바꿨는지, 어느 파일인지)

## 변경 이유
(왜 이렇게 만들었는지, 규약 문서의 어느 값을 따랐는지)

## 확인 방법
(실행해 본 명령과 그 결과를 그대로 붙여 넣는다)
- python -m compileall .
- python tools/check_imports.py
- python -m unittest discover -s tests
- (해당하면) 규약 문서 값과 대조한 결과

## 공통 모듈 변경일 때만
- 바뀐 함수: 
- 이 함수를 쓰는 기능:
```

- 한 PR에는 한 가지 변경만 담고, 변경은 300줄 이하로 한다.
- 기능을 추가하는 PR에는 그 기능의 테스트를 같은 PR에 넣는다.

각자 PR을 올리기 전에 `git config user.email`이 위 표의 이메일과 같은지 확인한다(다르면 기여로 인정되지 않는다). GitHub 아이디는 추후 확인되는 대로 추가한다.

- **고정 순번은 두지 않는다.** PR을 올린 사람이 위 표를 보고 검토자를 직접 지정해 리뷰 요청을 보낸다.
- **기능 PR**(`moim/features/`, `moim/commands/`): 자기 기능이 아닌 팀원 중 1명 이상을 지정한다. 그 기능과 의존 관계가 있는 사람(예: 기능 1의 PR이면 기능 4·5·6처럼 기능 1에 기대는 사람)을 우선 지정하면 검토가 더 의미 있다.
- 한쪽으로 몰리지 않게, 매주 수업 시간에 각자 지금까지 검토한 PR 건수를 서로 확인하고, 적게 검토한 사람을 다음 리뷰어로 먼저 지정한다.

### 검토 확인 항목

리뷰어는 승인하기 전에 아래를 확인하고, 코멘트에 **무엇을 확인했는지** 적는다.

- [ ] 자동 검사 3종(`compileall`, `check_imports.py`, `unittest discover`)이 모두 통과했는가
- [ ] PR 설명의 "확인 방법"에 실행 명령과 결과가 실제로 적혀 있는가
- [ ] 바뀐 값이 규약 문서(`docs/규약.md`)의 값·경계값과 맞는가
- [ ] 공통 모듈 변경 PR이면 "이 함수를 쓰는 기능"이 정확히 적혀 있고, 그 기능에 영향이 없는가
- [ ] 다른 사람이 담당한 기능 파일(`moim/features/`, `moim/commands/`)을 건드리지 않았는가

"확인했습니다"처럼 무엇을 봤는지 알 수 없는 승인은 검토 건수로 인정하지 않는다.

### 응답 기한

- 리뷰 요청을 받으면 **24시간 안에**(수업일 기준, 주말·공휴일 제외) 승인·변경 요청·질문 중 하나로 응답한다.
- 48시간이 지나도 응답이 없으면 PR 작성자가 다른 팀원을 리뷰어로 다시 지정한다.

## 5. 같은 파일을 여러 명이 고쳐 충돌이 생겼을 때

1. PR을 올리기 전에 먼저 `git pull origin main`으로 최신 main을 받아 로컬에서 충돌을 확인한다.
2. 충돌이 나면 `<<<<<<<`, `=======`, `>>>>>>>` 사이의 **두 변경을 모두 남기고** 합친다. 어느 한쪽을 지우지 않는다.
3. 합친 코드가 맞는지 모르면 **그 코드를 쓴 사람에게 먼저 묻는다.** 임의로 한쪽을 지우지 않는다.
4. 합친 뒤 `python -m compileall .`, `python tools/check_imports.py`, `python -m unittest discover -s tests`를 다시 돌려 통과를 확인하고 커밋한다.
5. 충돌이 잦은 두 파일은 특히 조심한다.
   - `moim/common/store.py`의 `EMPTY`: 기능 1·2·4·5가 각자 항목을 더한다. **한 PR에 한 항목만** 더하고, 올리기 전에 main을 받아 합친다.
   - `moim/common/queries.py`: 여섯 명이 각자 자기 함수만 채운다. 자기 함수가 아닌 부분은 건드리지 않는다.
6. 다른 사람이 맡은 기능 파일(`moim/features/`, `moim/commands/`)은 담당자의 승인 없이 고치지 않는다. 급하게 고쳐야 하면 담당자에게 요청하거나 PR에 의견을 남긴다.
